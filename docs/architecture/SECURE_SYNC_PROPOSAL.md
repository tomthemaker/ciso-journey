# Optional private sync — proposed Y01 design

Status: **PROPOSED, 2026-10-28**. Refs [Y01 / #22](https://github.com/tomthemaker/ciso-journey/issues/22), D009/D034 and O005 in [MEMORY](../product/MEMORY.md). This is a preparatory design for the static GitHub Pages app, not R5 delivery, infrastructure authorization or an accepted provider decision. [P01 / #18](https://github.com/tomthemaker/ciso-journey/issues/18) remains open; its event/portfolio model must be reconciled before implementing this proposal. Local study and private export/import remain the default and available without an account.

## Provider and identity proposal

The following comparison is an engineering judgment based on official documentation checked **2026-10-28**. Recheck availability, terms, operational limits and recovery options before selection; no pricing or legal-compliance guarantee is inferred.

| Option | Maintenance and identity | Location and recovery | Assessment |
|---|---|---|---|
| Supabase hosted Postgres + Auth | SQL transactions and per-account RLS fit related immutable events, references and conflict resolutions. Requires explicit sync protocol and policy testing. Email OTP is supported; production email requires a separately chosen SMTP service. | A specific Zurich `eu-central-2` or Frankfurt `eu-central-1` project region is listed. Database backup facilities depend on the selected plan; app exports remain necessary. | Provisional preference: one relational service with inspectable authorization/transactions. |
| Firebase Auth + Cloud Firestore | Credible managed alternative with browser offline support and account-based Security Rules. Its automatic last-write-wins document convergence cannot implement our review/note rules; a custom protocol remains necessary. Email-link identity is supported. | Firestore lists Zurich `europe-west6`; Firebase documents Auth processing in the US. Managed database exports require billing and a storage bucket; they are separate from learner exports. | Simpler generic offline client, but less aligned with relational constraints and existing F03 ownership of local state. |
| Remain local-only | Existing IndexedDB and v1/v2 exports; no identity service or backend to operate. | Browser/profile and learner-controlled backup locations; browser loss/eviction requires a private backup. | Lowest operational burden; manual device transfer, no automatic convergence. Valid continuing choice. |

Primary sources: Supabase [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [regions](https://supabase.com/docs/guides/platform/regions), [email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [backups](https://supabase.com/docs/guides/platform/backups); Firebase [Rules](https://firebase.google.com/docs/firestore/security/rules-conditions), [offline behavior](https://firebase.google.com/docs/firestore/manage-data/enable-offline), [email-link identity](https://firebase.google.com/docs/auth/web/email-link-auth), [locations](https://firebase.google.com/docs/firestore/locations), [Auth location](https://firebase.google.com/support/privacy), [managed export](https://firebase.google.com/docs/firestore/manage-data/export-import).

**Provisional recommendation:** Supabase, specific Zurich `eu-central-2`, verified email OTP, initially private learning metadata only. Zurich follows the Swiss learner context, not an established residency requirement. OTP avoids app-managed passwords and an additional social identity dependency; mailbox compromise/recovery becomes the main identity risk. Use a stable provider subject, never an email address, as ownership. Explicit account creation and opt-in enrollment must precede upload; ordinary sign-in must not silently create an account. No anonymous cloud accounts or automatic identity linking.

**Owner selection required before infrastructure:** provider, specific region, identity/recovery method, SMTP provider and recovery budget/retention. Primary database region does not establish locations for all authentication, email, logs, support access or backups; verify each, document subprocessors and applicable requirements separately. Do not advertise Swiss-only processing. Email OTP is not phishing-resistant; employer/confidential evidence is outside this initial scope. Lost mailbox access has no ad-hoc support override: use a previously exported copy in a new local profile, or a separately approved identity recovery process.

## Existing boundaries and required migration

Baseline `bc1b9de5889fe17be18c4d98940e3069edbc9b53`:

- [F03 storage](../../src/storage.ts) commits one schema-2 snapshot with a local revision check. It has no account namespaces, outbox, tombstones or remote transaction. The original `ciso-journey-v1` bytes are retained unchanged; storage is origin-scoped, not Pages-path-scoped.
- [LearnerState](../../src/types.ts) includes all 37 original completion IDs, six legacy scores, journal/achievements; independently versioned reading, resources, reviews, question attempts and case responses; and schema-1 display preferences. [Full backups](../../src/backup.ts) accept v1/v2 and preserve compatible unknown JSON fields.
- [S01](../../src/reviews.ts) validates exact per-card-revision before/after/log chains against pinned ts-fsrs 5.4.2 / FSRS-6.0 / adapter 1. [Questions](../../src/question-attempts.ts) and [cases](../../src/scenario-responses.ts) allow one self-assessment per submitted response. [Resources](../../src/resource-progress.ts) use sequential revision numbers, not globally unique revision/event IDs. Reading/task flags have no causal history today.

Y02 must first specify and test a versioned migration for account partitions, operation identities, causal references, conflicted histories and a complete backup envelope. Do not disguise these structures as compatible extra fields under today's validators. Preserve v1/v2 import and raw recovery bytes, all task meanings, exact content references, unknown compatible fields and historical scheduler provenance. Unsupported versions fail closed before writes; an old client cannot upload a snapshot over a newer model. Branched history cannot be exported as a lossless v2 snapshot: retain original imports, provide a new full format and explicitly label any deliberately limited legacy export. No downgrade by stripping conflicts.

P01 must decide how unresolved/unchosen branches and repeated assessments appear in time windows/sample sizes. Until then, no aggregate mastery/readiness score, automatic competency change or claim that every saved rating advanced the schedule. Future portfolio entities and binary uploads are not assumed implemented.

## Trust and authorization

All rules below are proposed application requirements, not guarantees supplied by selecting a vendor.

| Boundary / threat | Required control and limit |
|---|---|
| Unauthenticated client or account B forges account A identifiers | Deny anonymous learner access. Derive subject from verified authentication; authorize every read/write/export/RPC/subscription against the immutable owner and active account. Apply RLS `USING` and `WITH CHECK`; owner changes forbidden, including nested references. Composite owner/entity keys prevent cross-account references. Client filters and unguessable IDs are insufficient. |
| A client bypasses the UI or replays operations | Expose only minimal read privileges and bounded validated transactional mutation functions. Deny direct edits/deletes of immutable events, arbitrary projection writes and unscoped bulk operations. Functions must preserve caller authorization; any privileged function explicitly checks subject, account state, ownership and arguments. Fix function search paths and grants; test every exposed path. |
| Browser/source/build compromise | Only public project configuration and a publishable key enter the client. Secret/service-role/admin keys, database credentials and SMTP credentials stay server-side, never in Git, Vite variables, bundles or backups. Per-user session tokens are sensitive credentials, not authorization policy. |
| XSS, malicious imports, same-origin apps or a shared machine | Retain text rendering and safe URL validation; do not fetch private evidence URLs. Audit scripts/CSP feasibility on Pages and minimize dependencies. Partitioning is an app isolation control, not encryption against scripts on the same origin, developer tools, malware or the device owner. |
| Provider/operator access, outage or bad restore | No end-to-end encryption claim. Restrict operator access, require operator MFA, redact payloads/tokens from logs, use authenticated TLS, maintain private backups and rehearse recovery. Limit payload/batch sizes, rates and retries; preserve pending local work on outage/quota errors. |

Supabase documents that [publishable keys are public and secret keys bypass RLS](https://supabase.com/docs/guides/getting-started/api-keys). RLS ownership alone is not enough for append-only history: server constraints and transactional operations enforce the remaining invariants. Privileged maintenance/deletion has a separate narrowly scoped path, never a browser credential.

## Account lifecycle and durable operations

1. **Local to account:** show target account and a data inventory; export first and explicitly confirm copying a selected local profile. Do not upload on login or relabel the existing F03 snapshot. Validate and stage the copy transactionally with a stable migration ID; interrupted/repeated migration is idempotent. If the account already has data, reconcile entities under these conflict rules, never replace its full snapshot. Unknown extensions remain in private recovery/export and block automatic upload until classified, rather than leaking or discarding them.
2. **Account partition:** every local snapshot, draft, outbox entry, cursor and response carries `(provider/project, subject, dataset generation)`. Anonymous local study is a distinct partition. A queued operation's owner is immutable. Never drain account A's queue with account B's token or automatically copy it to B.
3. **Switch/sign-out:** freeze writes and cancel sync; advance a local session epoch, clear rendered data/drafts/tokens and notify other tabs. Reject late network callbacks and stale-tab commits against that epoch. Open B only after authentication and partition selection. Show a neutral screen on sign-out, not the old anonymous source copy. Proposed default retains A's cache/outbox hidden until A reauthenticates; disclose that retention and offer export then explicit removal, especially on shared devices. Never silently erase pending work. An account switch does not delete cloud data. The historical v1 source may also contain copied data; surface its presence in the separate device-erasure flow, without changing D021's retention promise implicitly.
4. **Offline/session expiry:** an already-open account can continue durable local work, visibly pending, while authentication expires. Upload pauses until that same subject reauthenticates. Explicit sign-out prevents account reopening without authentication; local study remains independently selectable. Offline app launch is not promised by durable storage and needs a separate caching/update design.
5. **Commit and retry:** a future IndexedDB transaction commits local observation/state plus its outbox operation before reporting saved. Envelope: stable operation ID, owner/generation, device ID, schema, entity ID, expected base/parent IDs, payload and observed timestamp. Server transaction checks authorization, schema, references and conflicts; stores immutable operation plus result/projection/tombstone and monotonic change cursor atomically. `(owner, generation, operation ID)` is unique: identical retry returns the same result; different payload under that ID fails without overwrite. Acknowledgement and incoming changes/cursor commit locally together. Crash after server commit and before acknowledgement therefore causes a harmless retry.
6. **Order:** server cursors order transport, not claimed learning time. Missing parents/response dependencies wait durably for replay; do not fabricate them. Device clocks/timestamps never select winners. Invalid events are isolated with a visible repair/export path; unsent work remains exportable. Bounded pages and transaction sizes prevent one bad batch blocking all independent entities.

Default sign-out requests this device's provider session scope; “sign out all devices” is a separate explicit action. Neither promises instant stolen-token revocation: Supabase [access tokens survive sign-out until expiry](https://supabase.com/docs/guides/auth/signout). Online account deletion instead requires a live active-account check on every data path, including subscriptions and privileged functions, so an otherwise valid old JWT cannot restore access. Clients cannot create/reactivate account-control rows or change dataset generations. Owner acceptance must include the sign-out residual window and configured expiry; failed/offline remote sign-out is shown as incomplete, while local isolation takes effect immediately.

## Conflicts without rewriting learning history

**Mutable values:** versioned compare-and-set per entity/field, not whole-snapshot last-write-wins. Causally ordered task/read toggles, scores, card status, new-card limit and display preference apply in sequence; contradictory concurrent values present a choice. Separate entities converge independently. Notes, journal entries, resource notes/evidence and metadata show the common base plus both versions with “keep this”, “keep other” or “save combined”. Resolution appends a revision naming both parents; retain originals until explicit erasure. No timestamp winner or automatic text concatenation.

**Attempts/assessments/resources:** distinct attempt/response IDs append once with exact content/rubric/provenance. Assessment arriving first waits for its response. Two offline self-assessments of one response exceed today's one-assessment invariant: preserve both proposed observations and require explicit active-assessment selection in a new schema, never append them into the old namespace or promote them to independent review. Concurrent resource revisions need immutable revision identities plus parent links; do not renumber and reinterpret historical `resourceVersion` references. These migrations are prerequisites, not implemented capabilities.

**Same card, two devices:** suppose both devices read head H. A records Good at 09:00 (`before=H`, `after=A1`); B offline records Again at 09:01 (`before=H`, `after=B1`). Both are valid observations. Concatenating A1/B1 breaks S01 because B1's `before` is not A1; sorting timestamps, recalculating B1 or dropping B1 silently would rewrite evidence.

Proposed resolution is **explicit branch selection**, not synthetic replay:

1. Store raw events exactly, including original IDs, rating, instant/timezone, scheduler parameters, before/after/log, and their branch ancestry. Validate each branch independently. Import existing S01 chains as roots with preserved enrollment state. Distinct offline enrollments of the same revision also require reconciliation.
2. A new child of the selected head extends that chain. A sibling/late child of an older head creates a conflict regardless of arrival order. Preserve all descendants, including multiple reviews performed offline on each branch. Missing parents wait; duplicate payloads are idempotent. Never backdate an event to force it into a chain.
3. While conflicted, suspend **new scheduled reviews of that card revision**, show both complete branches and hide its authoritative due/recall estimate. Other study continues. Explain that both sets of ratings remain observed history, but only one branch can currently drive scheduling.
4. Learner selects a complete branch/tip. Append a resolution referencing the full known conflict set and selected chain; use compare-and-set on the conflict generation. Concurrent resolutions cannot silently overwrite each other. The canonical schedule is the selected tip's unchanged `after`, with its pinned replay adapter. Nonselected ratings stay visible/exportable, explicitly excluded from scheduling. No automatic mastery changes.
5. Subsequent reviews refer to that resolution/head. A newly arriving unacknowledged branch reopens conflict; a retry of an already resolved event does not. A stale offline descendant is retained, not attached to a different head. Exact historical content remains addressable; no substitute current card revision.

This requires a new review representation, backup/validator support and P01 treatment of observed versus scheduling-selected history. It deliberately makes no promise of mathematically combining divergent FSRS states. Future automatic reprojection would need its own reviewed policy/version and must retain original observations separately.

## Deletion, exports and recovery

- **Archive is reversible; delete is distinct.** Deletion writes an owner/entity/generation tombstone in the same transaction as removing live access. It wins over concurrent edits and stale uploads; conflicts are not a route to resurrection. Confirmation explains dependent history: deleting a response includes its assessments; deleting a card's history includes its branches/projection. Ordinary note deletion must also remove prior note bodies from operation/conflict storage after the declared recovery window, not merely hide the current row.
- **Tombstone lifetime:** retain minimal IDs/generation/deletion cursor without note/evidence content. Proposed first version retains these markers for the account lifetime. If later compacted, expire old device cursors and require a full resync under a new generation; never accept an old queue against a truncated deletion history. Undelete/import is an explicit new entity/generation with provenance, not reuse of a tombstoned ID. Local reset, cloud dataset deletion and account deletion need separate labeled flows.
- **Account deletion:** recent reauthentication, export opportunity, explicit confirmation. First atomically disable the account and invalidate its dataset generation; then an idempotent privileged job removes live private data, queues/conflict payloads and authentication identity. Return completion only when all required stages succeed; retry failures, without re-enabling access. Supabase [deleting an Auth user alone does not immediately invalidate its JWT](https://supabase.com/docs/guides/auth/managing-user-data). Recreating the same email receives no ownership of the old subject. Offline devices cannot be remotely wiped; on reconnect, rejected old-generation work remains locally exportable or explicitly erasable, never auto-uploaded into a new account.
- **Recovery/export:** a learner-controlled full export includes all supported namespaces, exact historical refs, raw branches/resolutions, conflicts, tombstones, pending operation payloads and compatible extensions; excludes auth tokens/secrets. Distinguish local pending versus server-acknowledged data and any records already erased. Import first into an isolated staging/local profile, validate everything, preview reconciliation, and require explicit target-account consent. A backup is not authority to overwrite cloud deletions or set ownership. Use a consistent server cursor/snapshot for account export.
- **Operator restore:** rehearse isolated restore and reconciliation before serving traffic. Reapply deletion/account-disable records from a separately protected deletion ledger before reconnecting clients; rotate dataset generation where needed. Owner must choose backup/log/deletion-ledger retention and disclose erasure lag before launch. No immediate physical erasure from provider backups is promised; backups are not an undelete feature. No production release until retention and restore drills are verified.
- **Evidence privacy:** links/titles/notes only; no binaries, public buckets, preview fetching, analytics payloads or automatic link sharing. URLs can themselves reveal employer names or access tokens; warn before optional sync, allow local-only sensitive records, and exclude such content from diagnostics. Never put real learner files/evidence into this repository, CI artifacts or review comments.

## Future Y02 acceptance matrix

Synthetic accounts A/B and devices D1/D2; these are required tests, **not executed evidence**.

| Scenario | Required result |
|---|---|
| B guesses A IDs; anonymous and forged-owner read/insert/update/delete/export/RPC/subscription; cross-owner references | Denied server-side on every path; no row, payload or existence leak through a privileged fallback. |
| A queues offline on D1, then switches to B; delayed A response/stale tab; sign-out while sending | No A UI/cache/queue publication into B; immutable owner and epoch checks; A work remains recoverable. |
| Local migration crashes/retries; existing account has different data; backup contains unknown extensions | One explicit, validated migration; no silent replacement/upload of unclassified fields; raw source retained. |
| Server commits then reply is lost; duplicate ID with same/different body; out-of-order parent | Exactly one effect or explicit rejection; dependent events wait; cursor and acknowledgement recover after restart. |
| D1/D2 edit one note or disagree on a flag; clocks skew; concurrent resource revisions/assessments | Both revisions preserved with a visible resolution; no clock winner, invalid old-schema union or history retargeting. |
| D1 Good and D2 Again from H, later descendants; delivery order reversed; simultaneous resolution; late branch | Same raw history set, explicit conflict and valid selected chain; no lost rating, fabricated time/log or automatic competency change. |
| D1 deletes while D2 is offline editing; old backup/cursor replay; account deleted with still-valid JWT | Tombstone/active-account/generation gates prevent resurrection and access; no cloud deletion claim for offline device bytes. |
| Crash/quota during local commit or pull; session expires; provider unavailable | Atomic rollback or durable pending operation, explicit status and recovery export; useful local study continues. |
| New full backup round-trip, retained v1/v2 import, malformed/future versions, unknown historical content | All 37 IDs/six scores and separate learning signals retained; rejection before mutation; no silent downgrade. |
| Restore predates a deletion; stolen expired/revoked session; evidence URL/HTML injection; built bundle scan | Deletion ledger reapplied before access, authorization rechecked, safe rendering/no URL fetch, no privileged secrets. |

Y01 acceptance remains partial: this specifies behavior and a provisional choice; O005 selection and P01 reconciliation remain open.
